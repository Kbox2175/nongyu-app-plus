### 后端修复带来的新契约（本轮依据）

`cache_miss` 在校外形态（`mode=vpn`）下新增 `webvpn` 字段：

```json
{"code":"cache_miss","mode":"vpn","session":"client_side",
 "webvpn":{"status":"ready|missing|expired",
           "code":"webvpn_ticket_missing|webvpn_ticket_expired",  // ready 时无
           "expiresAt":"RFC3339"}}                                 // 仅 ready 时有
```

- `code` 与 `/fetch` 端点**完全同码**，客户端一套逻辑即可
- **诚实边界**（后端注释原话）：`cache_miss` 零出站，`status=ready` 只表示
  「本地保管着一张未被判死的票」，**不是**「网关保证放行」。真正判死靠后续请求遇到的 302

## 1 四项交付（维护者选的三项 + 一项修正）

### ① 课表刷新接入弹窗（`CourseRepository`）

在 `refreshFromJiaowu` 拿到 `cache_miss` 后判断 `miss.needsWebVpnLogin()`：
- `webvpn.code` 是 `webvpn_ticket_missing` → 投递 `WebVpnTrigger.TICKET_MISSING`
- `webvpn.code` 是 `webvpn_ticket_expired` → 投递 `WebVpnTrigger.TICKET_EXPIRED`
- `ready` / 校内形态（无 `webvpn` 字段）/ 未知 code → **不弹**

投递后**不阻塞**本次刷新（票可能其实还有效），失败提示仍由 UI 照常给。

### ② 修 `CourseRepository` 的错误注释

原文写「这个地址已经过 WebVPN 改写并带上票据」——**错的**。后端实际：
- 校内（`direct`）：直连 URL，**cookies 有值**
- 校外（`vpn`）：编码地址，**cookies 恒为空**（网关票只能由客户端自己登录网关产生）

已改正并写明两种形态。

### ③ 代取抽成通用能力（`net/core/RecipeFetcher`）

把 `CourseRepository` 里私有的 `fetchByRecipe` 抽到 `net/core/RecipeFetcher`。
理由：15 类回传数据用**同一个取数模型**，每加一类就复制一遍轮子必然分叉。

**⚠️ 分层约束**：`net/core` 是零依赖纯逻辑层，**不能接收 `CacheResult.Miss`**
（那会让 `core` 依赖 `net/model`）。所以接口只收原始参数：
`fetch(address, method, cookies: List<CookiePair>)`，由调用方摊平。

## 4 踩到的坑

1. **`net/core` 不能依赖 `net/model`**：第一版 `RecipeFetcher.fetch(recipe: CacheResult.Miss)`
   直接编译失败（`core` 里 `c.value` 解析不到）。改为收原始参数。
2. **MockWebServer 的 `setBody(String)` 不带 charset 时按平台默认编码**，
   而 `RecipeFetcher` 按 GBK 兜底解码 → 测试自身矛盾。
   修法：测字符集推断的用例显式写 `Content-Type: ...; charset=UTF-8`，字符集用例单独用 `Buffer().write(gbkBytes)`。
3. `RecipeFetcher` 第一版既声明 `private val client` 又写 `client()` 函数，后者未被使用；
   改为单一 `client()` 入口 + `setClientForTest`。
