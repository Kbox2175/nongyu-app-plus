# 皮肤包下载器：服务端对接须知（#53 的对端）

> 对应后端 `nongyu-backend-plus` 的 `internal/skin/`（issue #53 服务端实现）。
> 完整契约见后端 `docs/tech/皮肤包上传下载服务契约.md`。本文件只写**客户端
> 下载器要接的那一段**：首帧之后拉什么、拿到什么、怎么喂给既有
> `SkinPackIntegrity.verify` / `SkinPackPlanner.plan` / `SkinStore.install`。

## 0. 三条硬约束（别踩）

1. **首帧之前不碰网络**（ADR-0006）：下载器只能在首帧之后触发，且只写盘、
   不参与启动解析。冷启动仍从 `SkinStore.currentPackDir()` 读本地已装包。
2. **失败静默**（ADR-0003 / 0006 Q3=B）：拉目录失败 / 下载失败 / 校验失败
   一律只记日志，**不动当前生效的包**。`SkinStore.install` 已保证原子性，
   调用方只要「结论不 OK 就不调 install」即可。
3. **完整性在应用侧判**：`downloadUrl` 只是「谁能取」。整包是不是官方包，
   由客户端用 `manifest.integrity.signature` + 内置验签公钥判；服务端**不验
   签名的真伪**，只保证签名非空并原样透传。

## 1. 端点（App 侧只读，无用户会话也要能调）

| method | path | 鉴权 |
| --- | --- | --- |
| GET | `/skins/current` | 免用户会话（`publicReadablePaths` 只放行 GET/HEAD），但仍需 NY1 请求签名 |
| GET | `/skins/:packId/:version` | 同上，单包详情 |
| GET | `/skins/:packId/:version/pack` | 同上，包体 zip 流式下载 |

> 与登录无关：设备可能还没登录，所以这三个端点**不需要 Bearer token**，
> 但仍必须带 NY1 四个签名头（见 `docs/后端已就绪-前端对接须知.md` §2）。
> 服务端把 `/skins` 加进了「公开可读」清单，写操作（`/admin/*`）不在其中。

## 2. 目录接口响应 `GET /skins/current`

```json
{
  "hasPack": true,
  "packId": "default-green",
  "version": "1.0.0",
  "schemaVersion": 1,
  "minAppVersion": 1,
  "displayName": "农屿默认绿",
  "packSha256": "<整个 zip 的 sha256>",
  "packSize": 12345,
  "manifest": { ... },
  "downloadUrl": "/skins/default-green/1.0.0/pack",
  "updatedAt": "2026-11-16T..."
}
```

- **`hasPack: false`**（HTTP 200，不是 404）= 服务端还没发布任何皮肤。
  直接回落内置默认皮肤，**不要发第二次请求、不要伪造空包**。
- `manifest` 就是包内 `manifest.json` 的原文（服务端不重新序列化），
  可直接喂给 `SkinManifestParser.parseJson(...)`（用 `org.json.JSONObject`，
  注意纯 JVM 单测里它是 stub，判定逻辑走 `parseMap`）。
- `version` 对应落盘路径 `filesDir/skins/{packId}/{version}/`，
  与 `SkinStore.install(unpackedDir, packId, version)` 的第二、三参一致。
- `downloadUrl` 是相对路径，需拼上 base URL；也可直接按
  `{base}/skins/{packId}/{version}/pack` 构造。

## 3. 包体下载 `GET .../pack`

- `Content-Type: application/zip`，body 是 zip 字节。
- 响应头 `X-Nongyu-Pack-Sha256: <整包 sha256>`：落临时目录前先比对，
  不符即丢弃（省掉一次解包）。
- 下到**临时目录**（不是 `cacheDir`、不直接进 `skins/`），解压后得到
  「包根」目录。

## 4. 接到既有代码的标准链路（#53 交付 1）

```
首帧后触发（LaunchedEffect / WorkManager / 首帧回调，具体实现自选）
  └─ GET /skins/current
       ├─ hasPack=false → 回落内置默认，结束
       └─ hasPack=true
            ├─ GET downloadUrl → 临时目录 zip
            │    ├─ 比对 X-Nongyu-Pack-Sha256
            │    └─ 解压到临时目录（注意挡目录穿越，服务端已挡过，客户端再挡一次）
            ├─ SkinManifestParser.parseJson(manifest) → SkinPackManifest
            │    （用目录返回的 manifest；也可读包内 manifest.json，二者一致）
            ├─ SkinPackIntegrity.verify(
            │       SkinPackVerifyInput(manifest, actualBytes, BuildConfig.VERSION_CODE),
            │       verifier /* 内置公钥验签 */)
            ├─ verification.ok == false → 记日志，结束（不调 install）
            └─ verification.ok == true
                 ├─ SkinPackPlanner.plan(...) → LoadedResources（可选，用于装配）
                 └─ SkinStore.install(unpackedDir, manifest.packId, catalog.version)
                      → InstallOutcome.Installed / Unchanged
```

要点：

- `SkinPackIntegrity.verify` 的 `actualBytes` 用 `FilePackByteSource.read`
  按 `manifest.entries[].path` 取字节（既有 `SkinPackLoader.assemble` 已做）。
- `minAppVersion` 判定权在客户端（ADR-0003）：`verify` 内部用
  `BuildConfig.VERSION_CODE` 比 `manifest.minAppVersion`，服务端不替你判。
- `schemaVersion > SUPPORTED_SCHEMA_MAJOR` 时 `verify` 返回
  `SchemaTooNew` → 整包回落；服务端入库时已挡过主版本过高，这是双保险。
- **只在 `verification.ok` 时**调 `SkinStore.install`；失败分支绝不碰指针。

## 5. 与 #41（网络层选型）的关系

票 #53 评论里提过「HTTP 能力可能与 #41 分叉」。本服务端接口是普通
`GET` + JSON / 二进制，**不绑定任何特定 HTTP 客户端**：无论 #41 最后选
OkHttp / Retrofit / Ktor / HttpURLConnection，只要能发 NY1 签名头的 GET、
能读响应体字节即可。下载器建议把「发请求」抽成一个窄接口（如
`SkinCatalogFetcher`），决策部分（校验 / 降级 / 是否 install）保持纯 JVM
可测，与 IO/网络解耦——这正是 #53 验收「新增逻辑有纯 JVM 单测覆盖」的要求。

## 6. B 端上传（仅供调试 / 造测试数据）

管理台 `POST /admin/skins`（multipart：`version`、`activate`、`file`），
需 admin 会话 + role。传一个合法皮肤包 zip（根含 `manifest.json` +
`integrity.entries` 声明的资源文件）即可；`activate=true` 会让
`/skins/current` 立刻指向它。回滚用
`POST /admin/skins/{packId}/{oldVersion}/activate`，无需重传。

包体格式、白名单扩展名、整包签名约定见后端契约文档 §2。
